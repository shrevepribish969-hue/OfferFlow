# OfferFlow Domain Model & Data Schema（Version 1.0）

## 1. Design Philosophy

OfferFlow 采用 Domain Driven 的数据设计思想，整个系统并不是围绕页面或功能模块组织数据，而是围绕求职过程中真实存在的业务对象（Domain Object）组织数据。

在传统产品中，数据库通常按照页面拆分，例如岗位表、面试表、日历表等，每个页面维护自己的数据。而在 OfferFlow 中，一个对象可能同时服务于多个页面，也可能被多个 Agent 和 Skill 共同使用。因此，本系统首先定义业务对象，再由业务对象衍生数据库结构，而不是反过来由数据库决定产品逻辑。

整个系统以 **Job Case** 为核心对象，其余所有对象均围绕 Job Case 展开，共同构成一个完整的求职知识网络。

---

## 2. User Profile

User Profile 是用户的长期身份信息，也是所有 AI 推理的基础上下文。

它记录的是用户不会因为某一次岗位投递而频繁变化的信息，包括教育背景、工作经历、项目经历、技能标签、个人优势、目标岗位方向以及母版简历等内容。

User Profile 并不直接参与某一次 Job Case 的业务流程，而是作为全局上下文供所有 Job Case 共享。Resume Agent 在分析岗位时，会读取 User Profile 获取用户已有能力；Interview Agent 在生成模拟面试时，也会结合 User Profile 调整问题难度和方向。

整个产品生命周期内通常只有一个 User Profile，它是 AI 理解用户的起点，也是 Memory 的重要组成部分。

---

## 3. Job Case

Job Case 是 OfferFlow 的核心对象，也是整个系统唯一的业务中心。

每一次岗位投递都会生成一个独立的 Job Case，它代表用户与某一个岗位之间的完整求职过程。Job Case 包含岗位基本信息、岗位描述（JD）、当前状态、目标城市、招聘渠道、岗位链接、投递时间、提醒策略以及所有与该岗位相关的数据。

除此之外，Job Case 还维护与其他对象之间的关联关系，包括当前使用的 Resume、历史 Interview、Communication、Reflection 以及待完成的 Task。

Job Case 本身并不保存所有详细内容，而是作为一个聚合根（Aggregate Root），统一管理整个岗位生命周期中的所有业务对象。

Job Case 生命周期从用户创建岗位开始，经过岗位分析、简历优化、正式投递、面试、Offer 或 Rejected，最终进入 Archived 状态。任何状态变化都会触发对应 Workflow。

---

## 4. Resume

Resume 对象代表用户针对某一个 Job Case 所生成的简历版本。

OfferFlow 不认为用户只有一份简历，而是认为每一个 Job Case 都可能拥有独立的 Resume Version。系统始终保留用户母版简历，同时允许 AI 根据不同岗位生成不同版本，并保存版本历史。

Resume 除了保存最终内容之外，还记录 AI 对本次优化所做出的修改，例如新增关键词、强化项目经历、调整表达方式以及修改原因。这些内容能够帮助用户理解 AI 的优化逻辑，而不是仅仅得到一份最终结果。

Resume 与 Job Case 为一对多关系，一个岗位可以拥有多个历史版本，但始终存在一个 Current Resume 作为当前投递版本。

---

## 5. Interview

Interview 对象用于记录某一次具体的面试过程。

每一次面试都会生成一个独立 Interview 对象，其中包括面试轮次、时间、面试形式、面试官信息、问题记录、用户回答、AI 评价以及最终结果。

Interview 不属于整个求职流程，而属于某一个具体节点，因此一个 Job Case 可以关联多个 Interview。例如，一家公司可能同时经历一面、二面和 HR 面，每一次都会生成新的 Interview 对象。

Interview 的主要作用不是保存聊天记录，而是为 Reflection 提供输入数据，同时为后续面试训练提供真实案例。

---

## 6. Communication

Communication 用于记录用户与 HR、招聘系统以及面试官之间发生的正式沟通。

它包括邮件、微信、电话、招聘平台消息、Offer 沟通以及 Follow-up 邮件等内容。

Communication 的重点并不是保存所有聊天内容，而是记录关键事件，例如发送时间、发送对象、沟通目的以及当前状态。

系统能够根据 Communication 自动判断是否需要提醒用户 Follow-up，也能够帮助 AI 在生成后续邮件时理解双方历史沟通背景。

Communication 属于 Job Case，因此不同岗位拥有各自独立的 Communication Timeline。

---

## 7. Reflection

Reflection 是 OfferFlow 中最重要的知识沉淀对象。

每完成一次 Interview，系统都会引导用户进行复盘，并结合 AI 自动生成 Reflection。

Reflection 并不评价用户"表现好不好"，而是客观总结本次面试出现的问题，包括高频知识点、表达不足、案例准备情况、技能缺口以及后续建议。

Reflection 永远对应一次 Interview，因此一个 Interview 只产生一个 Reflection，而一个 Job Case 可以拥有多个 Reflection。

Reflection 不仅帮助用户总结经验，也是 Memory 更新的重要来源。

---

## 8. Memory

Memory 是整个 AI 系统的长期知识库。

Memory 不保存聊天记录，也不保存完整历史，而只保存具有长期价值的信息。

例如，AI 可以根据多个 Reflection 总结用户长期存在的能力短板，也可以记录用户偏好的表达方式、长期职业方向以及已经掌握的知识点。

Memory 并不会因为一次对话而自动更新，而是由 Workflow 在关键节点主动写入。例如，当 Reflection 完成后，系统会提取长期有效的信息写入 Memory，而不是直接保存整篇复盘内容。

Memory 的存在，使 AI 不需要重复分析用户过去所有经历，而能够持续理解用户成长轨迹。

---

## 9. Task

Task 是 Workflow 自动生成的执行对象。

Task 可以来源于用户主动创建，也可以由 AI 自动生成。

例如，当岗位进入 Applied 状态后，Workflow 会自动创建 Follow-up Task；当岗位进入 Interview 阶段后，系统会自动生成模拟面试任务；当用户完成面试后，系统会自动生成 Reflection Task。

Task 不属于 AI 推理，而属于 Workflow 调度，因此它是连接 AI 与用户执行行为的重要桥梁。

Task 包括任务名称、优先级、截止时间、所属 Job Case、完成状态以及触发来源。

---

## 10. Relationship Design

整个系统采用以 Job Case 为中心的聚合设计。

User Profile 为所有 Job Case 提供全局信息，每一个 Job Case 拥有自己的 Resume、Interview、Communication、Reflection 以及 Task。

Reflection 能够更新 Memory，而 Memory 又会反过来影响 Resume Analysis、Interview Preparation 等 Skill 的推理结果，形成完整的知识闭环。

因此，OfferFlow 并不是多个独立页面的数据集合，而是由多个业务对象共同组成的求职知识网络。

这种设计能够保证所有 Agent 都围绕统一的数据模型工作，也能够方便未来增加新的 Skill，而无需重新设计数据库结构。

---

## 11. Data Design Principles

OfferFlow 的数据设计遵循五项原则。

第一，所有数据围绕业务对象组织，而不是围绕页面组织。

第二，Job Case 是唯一的业务中心，所有对象均依附于 Job Case 生命周期。

第三，对象之间保持低耦合、高聚合，每个对象只负责自己的业务边界。

第四，Memory 只保存长期知识，不保存完整聊天记录，避免上下文污染。

第五，任何新增功能应优先复用已有对象，而不是新增新的数据模型，从而保证整个系统具有良好的扩展性与长期可维护性。
