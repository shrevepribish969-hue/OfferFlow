# OfferFlow AI Architecture Design（Version 1.0）

## 1. Architecture Overview

OfferFlow 是一款 AI Native 求职工作台，其核心设计目标并不是构建一个能够回答所有问题的大语言模型聊天机器人，而是构建一个能够长期协助用户完成求职任务的 AI Workspace。

传统 AI 产品通常以一次对话（Conversation）作为交互单位，用户每一次提出问题，AI 独立完成回答，缺乏长期上下文和任务管理能力。而求职本身是一个持续数周甚至数月的复杂流程，每一个岗位都会经历岗位分析、简历准备、投递、面试、沟通、复盘等多个阶段。因此，OfferFlow 将整个系统设计为 **Job Case Driven**，即以每一次岗位投递作为核心对象，而不是以聊天记录作为核心对象。

整个系统采用分层架构设计，用户始终通过统一的 AI Assistant 与系统交互，后台由 Workflow Engine 根据 Job Case 当前状态自动调度不同 Agent，Agent 再调用对应 Skill 完成具体任务，Skill 最终通过 Prompt、Memory、Tool Call 与 Gemini 大模型交互，并将结果保存至 Supabase。

整个系统遵循：

**User → AI Assistant → Workflow → Agent → Skill → Prompt / Memory / Tool → Gemini → Database**

这一执行路径，使业务逻辑、AI 推理和系统能力完全解耦。

---

# 2. Domain Model（核心对象设计）

OfferFlow 的所有数据围绕对象（Object）展开，而不是围绕聊天记录展开。每一个对象都有明确的职责、生命周期和数据边界。

目前 MVP 版本包含以下核心对象：

| Object        | 描述                            | 生命周期    |
| ------------- | ----------------------------- | ------- |
| User Profile  | 用户长期基础信息，包括母版简历、教育经历、项目经历、技能等 | 长期存在    |
| Job Case      | 一次岗位投递的完整生命周期                 | 创建至归档   |
| Resume        | 当前 Job Case 所使用的简历版本          | 可不断迭代   |
| Interview     | 某一次具体面试的信息                    | 面试结束后固定 |
| Communication | 与 HR、面试官之间的沟通记录               | 持续更新    |
| Reflection    | 单次面试后的复盘结果                    | 面试结束生成  |
| Memory        | AI 长期记忆，仅保存长期有效信息             | 持续维护    |

其中，**Job Case 是整个系统最重要的核心对象**。

每创建一次新的岗位投递，系统都会自动创建一个 Job Case。所有 AI 工作均围绕当前 Job Case 展开，包括岗位分析、简历优化、面试准备以及复盘总结。

---

# 3. Job Case Lifecycle

Job Case 具有完整生命周期。

每一个 Job Case 会经历如下状态：

```text
Created

↓

Prepared

↓

Applied

↓

Assessment

↓

Written Test

↓

Interview

↓

HR Interview

↓

Offer

↓

Rejected / Archived
```

每一次状态变化都会触发对应 Workflow。

例如：

* Created → 自动解析 JD
* Applied → 自动创建 Follow-up Task
* Interview → 自动进入 Interview Workflow
* Offer → 自动归档 Job Case

因此，Job Case 不只是数据库中的一条记录，而是整个 AI Workflow 的驱动中心。

---

# 4. Agent Architecture

OfferFlow MVP 仅包含四个业务 Agent。

用户始终只看到一个 AI Assistant，而不会感知 Agent 的存在。

后台根据当前 Job Case 所处阶段自动调用对应 Agent。

| Agent               | 主要职责                       |
| ------------------- | -------------------------- |
| Case Manager        | 管理 Job Case 生命周期及 Workflow |
| Opportunity Analyst | 分析岗位需求及岗位匹配度               |
| Resume Strategist   | 根据岗位优化 Resume              |
| Interview Coach     | 面试准备、评价及复盘                 |

Agent 是业务能力的组织方式，而不是 AI 能力本身。

真正完成 AI 推理的是 Skill。

---

# 5. Skill Library

Skill 是 OfferFlow 最小的 AI 能力单元。

每一个 Skill 都拥有独立 Prompt、输入参数、输出参数以及 Tool Call，可以被多个 Agent 重复调用。

整个 MVP 版本共包含十个核心 Skill。

| Skill                 | 所属 Agent                                | 职责                        |
| --------------------- | --------------------------------------- | ------------------------- |
| Job Case Management   | Case Manager                            | 创建、更新、归档 Job Case         |
| Workflow Planning     | Case Manager                            | 创建 Task、提醒、状态流转           |
| JD Analysis           | Opportunity Analyst                     | 解析岗位 JD，提取岗位要求            |
| Job Matching          | Opportunity Analyst / Resume Strategist | 分析 Resume 与 JD 的匹配程度      |
| Resume Analysis       | Resume Strategist                       | 解析 Resume，提取能力标签          |
| Resume Optimization   | Resume Strategist                       | 优化 Resume 内容及结构           |
| Content Generation    | Resume Strategist / Interview Coach     | 生成简历、自我介绍、Follow-up 邮件等内容 |
| Interview Preparation | Interview Coach                         | 根据 JD 生成模拟面试及准备计划         |
| Interview Evaluation  | Interview Coach                         | 评价回答质量并提出建议               |
| Reflection            | Interview Coach                         | 对单次面试进行复盘，并沉淀经验           |

整个 Skill Library 是 OfferFlow 最重要的 AI 能力资产。

未来新增 Agent 时，应优先复用已有 Skill，而不是新增 Skill。

---

# 6. Workflow Design

Workflow 是整个系统的大脑。

OfferFlow 明确规定：

**Workflow 永远由程序控制，而不是由 LLM 自主规划。**

Gemini 负责推理。

Workflow 负责调度。

例如，新建 Job Case 后：

```text
Create Job Case

↓

JD Analysis

↓

Resume Analysis

↓

Job Matching

↓

Resume Optimization

↓

Generate Resume

↓

Complete
```

进入 Interview 阶段后：

```text
Update Stage

↓

Interview Preparation

↓

Generate Mock Questions

↓

Create Interview Tasks

↓

Complete
```

面试结束后：

```text
Upload Interview Notes

↓

Interview Evaluation

↓

Reflection

↓

Update Memory

↓

Complete
```

Workflow 保证整个 AI 系统具有稳定、可预测和可维护的执行流程，而不会因为模型不同产生随机行为。

---

# 7. Prompt Architecture

Prompt 是 OfferFlow 的核心资产，因此采用独立管理，而不是硬编码到业务逻辑中。

每一个 Skill 对应一份独立 Prompt 文件。

例如：

* jd-analysis.md
* resume-analysis.md
* resume-optimization.md
* interview-preparation.md
* reflection.md

所有 Prompt 统一采用以下结构：

Role：定义 AI 身份。

Goal：定义任务目标。

Input：说明输入数据。

Workflow：规定推理步骤。

Constraint：约束 AI 行为。

Output：统一输出格式。

这种设计能够实现 Prompt 与代码解耦，方便版本管理及持续优化。

---

# 8. Memory Architecture

Memory 并不是聊天记录，而是 AI 长期知识库。

Memory 仅保存具有长期价值的信息，例如：

* 用户能力标签
* 长期职业目标
* 历史 Reflection
* 高频能力短板
* 长期学习建议

Memory 存储于 Supabase。

Skill 在执行前可主动读取 Memory。

Memory 的更新必须由 Workflow 控制，而不是每次聊天自动写入。

这种设计能够有效避免 Memory 污染，提高长期上下文质量。

---

# 9. Tool Calling Strategy

Tool 是 AI 与系统之间的执行接口。

Gemini 不直接修改数据库，而是通过 Tool 完成系统操作。

目前系统规划的核心 Tool 包括：

* Read Job Case
* Update Job Case
* Read Resume
* Save Resume
* Read Memory
* Update Memory
* Create Task
* Save Reflection
* Call Gemini

Skill 可以根据需要调用多个 Tool，但所有数据库操作必须通过 Tool 完成，而不能由 Prompt 控制。

---

# 10. Technical Architecture

OfferFlow 采用前后端分离架构。

React + TypeScript 负责前端页面。

Supabase 负责数据库。

Gemini 负责模型推理。

Prompt 独立存放于 Markdown。

Memory 统一存储于 Supabase。

Workflow 独立管理。

Skill 独立封装。

React 前端仅负责调用 API，不直接调用 Gemini，不直接管理 Prompt，也不直接访问 Memory。

Antigravity 负责根据本架构完成工程实现，而所有 AI 设计（Agent、Skill、Workflow、Prompt、Memory）均以本设计文档为最高规范。

---

# 11. Design Principles

OfferFlow 的整体设计遵循以下原则：

第一，以 Job Case 而不是 Conversation 作为 AI 的核心对象，使 AI 能够围绕岗位生命周期持续工作。

第二，以 Skill 而不是 Agent 作为最小 AI 能力单元，提高 Prompt 与能力复用率。

第三，由 Workflow 控制流程，由 Gemini 负责推理，实现业务逻辑与模型能力解耦。

第四，Prompt 独立管理，Memory 长期维护，Tool 统一执行，确保系统具有良好的可维护性与可扩展性。

第五，任何新增功能都应优先复用已有 Skill，而不是新增 Agent，保证整个系统能够随着产品迭代持续演进，而不会形成复杂、难维护的 AI 架构。
