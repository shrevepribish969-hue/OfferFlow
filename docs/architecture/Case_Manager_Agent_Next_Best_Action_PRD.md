# Case Manager Agent 与下一步建议 PRD

## 1. 产品目标

本 PRD 说明 OfferFlow 下一阶段最核心的 Agent 化能力：

> 让右侧 Copilot 从“被动聊天助手”升级为“Case Manager Agent”，能够观察当前 Job Case 状态，判断下一步最该做什么，并向用户解释原因。

这个能力不要求 AI 立刻自动执行所有任务。

第一阶段目标是：

- Agent 先观察
- Agent 给建议
- Agent 解释理由
- 用户确认后再执行

这样可以在不破坏现有 workflow 的前提下，让产品明显更像 Agent。

## 2. 背景问题

当前三栏工作台已经很适合求职流程：

- 左侧是流程阶段
- 中间是阶段产物卡片
- 右侧是 AI Copilot

但当前用户仍然需要自己判断：

- 现在该点哪个阶段？
- 这个岗位是否值得继续？
- 简历优化前是否应该先做岗位匹配？
- 面试复盘后哪些内容应该沉淀为长期记忆？
- 多个 Job Case 里哪个最需要跟进？

也就是说，系统已经能执行任务，但还不够会“判断下一步”。

Case Manager Agent 要解决的就是这个问题。

## 3. 核心用户价值

### 3.1 降低求职流程负担

用户不用一直自己想下一步做什么。

系统可以直接告诉用户：

> 当前最建议先做岗位匹配，因为后续简历优化需要匹配结果作为依据。

### 3.2 让 AI 更像任务伙伴

AI 不只是回答问题，而是主动观察当前任务状态，并提出行动建议。

### 3.3 让流程更可控

Agent 不直接替用户做决定，而是先给建议和理由，再让用户确认。

这对求职场景很重要，因为简历、投递、面试表达都属于高风险内容，不能让 AI 完全自动替用户决定。

## 4. 一句话用户体验

用户进入某个 Job Case 后，右侧 Copilot 顶部出现一个“当前建议”模块：

> 我检查了当前岗位进度。现在建议先完成岗位匹配，因为 JD 已经分析完成，但还没有判断你和岗位的匹配度。完成匹配后，再做简历优化会更准确。

按钮：

- 开始岗位匹配
- 稍后再说
- 为什么这么建议？

## 5. 页面位置

建议放在右侧 AI Copilot 顶部，聊天消息列表上方。

原因：

- 用户已经习惯在右侧和 AI 沟通
- 不会破坏当前中间卡片区
- 可以保持现有三栏结构
- 适合展示 Agent 的判断和解释

页面结构：

```text
左侧 Workflow      中间工作产物区              右侧 Copilot
---------------------------------------------------------------
JD 分析            JD 分析卡片                 当前建议
岗位匹配           简历优化卡片                AI 对话
简历优化           面试准备卡片                快捷操作
投递状态
面试流程
Offer 跟进
```

## 6. 功能范围

### 6.1 第一阶段要做

- 读取当前 Job Case 状态
- 判断当前缺失步骤
- 生成下一步建议
- 展示推荐理由
- 提供用户确认按钮
- 用户确认后触发现有 workflow

### 6.2 第一阶段不做

- 不让 Agent 自动投递
- 不让 Agent 自动修改最终简历
- 不让 Agent 静默写入长期记忆
- 不替换现有 workflow
- 不做完全自主多 Agent 协作

第一阶段原则：

> Agent 先做建议者，不做完全自动执行者。

## 7. 判断逻辑

Case Manager Agent 可以先用规则判断，不一定一开始就全部依赖大模型。

原因：

- 更稳定
- 更容易解释
- 更适合求职流程
- 不容易误判

### 7.1 状态信号

Agent 可以观察这些信息：

- 是否有 JD 内容
- 是否已有 JD 分析结果
- 是否已有岗位匹配结果
- 是否已有简历优化建议
- 是否已有最终简历版本
- 是否已投递
- 是否有面试轮次
- 是否已有面试准备包
- 是否已有面试复盘
- 是否已有 Reflection
- 是否已有长期 Memory
- 当前 Job Case 状态
- 最近一次 TimelineEvent

### 7.2 推荐规则示例

#### 场景 1：没有 JD 内容

推荐：

> 请先导入或粘贴 JD。

理由：

> 没有岗位信息，系统无法进行岗位分析、匹配和简历优化。

主按钮：

> 导入 JD

#### 场景 2：有 JD，但没有 JD 分析

推荐：

> 建议先分析 JD。

理由：

> JD 分析会提取岗位职责、核心能力和关键词，是后续匹配和简历优化的基础。

主按钮：

> 开始 JD 分析

#### 场景 3：有 JD 分析，但没有岗位匹配

推荐：

> 建议进行岗位匹配。

理由：

> 需要先知道你的简历和岗位之间的匹配度、优势和短板，再决定是否继续投入精力。

主按钮：

> 开始岗位匹配

#### 场景 4：有岗位匹配，但没有简历优化

推荐：

> 建议进行定向简历优化。

理由：

> 当前已经知道岗位要求和你的能力缺口，可以基于这些信息生成更有针对性的简历修改建议。

主按钮：

> 优化简历

#### 场景 5：有简历优化建议，但用户未确认

推荐：

> 建议先审核简历优化建议。

理由：

> AI 生成的职业内容需要用户确认，尤其要检查是否存在夸大或不准确表达。

主按钮：

> 查看修改建议

#### 场景 6：简历已确认，但未投递

推荐：

> 建议生成投递沟通话术。

理由：

> 当前简历已经准备好，可以生成适合该岗位的打招呼语或邮件，提升投递效率。

主按钮：

> 生成打招呼语

#### 场景 7：已投递，但没有面试

推荐：

> 建议设置跟进提醒。

理由：

> 投递后需要管理后续沟通节奏，避免忘记跟进。

主按钮：

> 添加跟进任务

#### 场景 8：有面试，但没有面试准备

推荐：

> 建议生成本轮面试准备包。

理由：

> 面试准备需要结合岗位要求、简历亮点和真实面经问题。

主按钮：

> 生成面试准备

#### 场景 9：面试结束，但没有复盘

推荐：

> 建议进行面试复盘。

理由：

> 面试复盘可以提取表现问题和改进方向，并用于后续面试准备。

主按钮：

> 开始面试复盘

#### 场景 10：有复盘，但没有 Memory 确认

推荐：

> 建议确认是否保存长期记忆。

理由：

> 这次面试暴露的问题可能会在后续面试中重复出现，确认后系统可以持续提醒和优化。

主按钮：

> 查看记忆候选

## 8. 推荐卡片内容结构

右侧 Copilot 顶部可以展示一张 Agent 建议卡。

字段：

- 当前状态
- 推荐动作
- 推荐理由
- 风险提醒
- 主按钮
- 次按钮
- 解释入口

示例：

```text
当前建议

状态：
JD 已完成分析，但还没有岗位匹配结果。

建议：
先进行岗位匹配。

原因：
简历优化需要基于岗位匹配结果，否则容易变成泛泛改写。

风险提醒：
如果跳过匹配直接优化，AI 可能无法准确判断哪些经历最该突出。

[开始岗位匹配] [稍后再说] [为什么这么建议？]
```

## 9. 用户交互

### 9.1 用户点击主按钮

系统触发现有 workflow。

例如：

- 开始 JD 分析 -> 触发 JDAnalysis
- 开始岗位匹配 -> 触发 JobMatching
- 优化简历 -> 触发 ResumeOptimization
- 生成面试准备 -> 触发 InterviewPrep

### 9.2 用户点击稍后再说

系统暂时隐藏本次建议，但不改变 Job Case 状态。

可以记录一个轻量反馈：

> 用户暂时忽略该建议。

### 9.3 用户点击为什么这么建议

Agent 展开更详细解释：

- 当前系统看到了什么
- 为什么这个动作优先级最高
- 如果跳过会有什么风险
- 后续会进入哪个阶段

## 10. 和现有 Workflow 的关系

Case Manager Agent 不替换现有 workflow。

它只是站在 workflow 前面，帮用户判断：

- 现在该不该执行这个 workflow
- 为什么执行这个 workflow
- 执行完之后下一步是什么

关系可以理解为：

```text
Case Manager Agent：判断下一步
Workflow：执行具体任务
SkillExecutor：调用具体 AI 能力
Prompt：约束 AI 输出格式和内容
Database：保存结果
Frontend Card：展示结果
```

## 11. 和多 Agent 的关系

第一阶段不需要真正做复杂多 Agent 协作。

可以先把 Case Manager Agent 做成统一入口。

未来再拆成：

- Case Manager Agent：判断下一步
- Resume Agent：负责简历
- Interview Agent：负责面试
- Reflection Agent：负责复盘和记忆
- Communication Agent：负责沟通

面试中可以这样讲：

> 当前版本先实现 Case Manager Agent，因为它最贴近用户决策。专业 Agent 可以逐步接入，但不需要一开始做复杂的多 Agent 系统。

## 12. 数据记录建议

即使第一阶段不改复杂数据库，也建议未来记录这些信息：

- Agent 推荐了什么
- 推荐理由是什么
- 用户是否点击执行
- 用户是否忽略
- 最终 workflow 是否成功
- 用户是否对结果满意

这些记录可以支持后续：

- 推荐策略优化
- Badcase 分析
- 用户行为分析
- Agent 质量评估

## 13. 成功指标

### 13.1 产品指标

- 用户是否更容易知道下一步做什么
- 用户是否更频繁完成完整 Job Case 流程
- 用户是否更少卡在某个阶段
- 用户是否更愿意接受 AI 建议

### 13.2 AI 指标

- 下一步建议是否合理
- 推荐理由是否清楚
- 用户采纳率
- 用户忽略率
- 推荐后 workflow 成功率
- Badcase 数量和类型

### 13.3 面试展示指标

可以这样表达：

> 我把 Agent 的效果拆成三类指标：推荐是否合理、用户是否采纳、采纳后是否推动 Job Case 前进。这样可以避免只用“生成质量”评价 Agent，而是从任务推进效果评价 Agent。

## 14. 风险与边界

### 14.1 风险：Agent 误导用户

解决：

- 第一阶段只推荐，不自动执行
- 给出推荐理由
- 让用户确认

### 14.2 风险：AI 自动修改关键内容

解决：

- 简历修改必须用户确认
- Memory 写入必须用户确认
- 投递和发送消息必须用户确认

### 14.3 风险：用户不理解为什么推荐

解决：

- 每个建议都附带一句明确理由
- 提供“为什么这么建议？”展开入口

### 14.4 风险：规则太死板

解决：

- 第一阶段用规则保证稳定
- 后续结合 LLM 生成更自然的解释
- 根据用户反馈优化推荐策略

## 15. MVP 范围

最小可用版本只需要完成：

1. 在右侧 Copilot 顶部展示一张“当前建议”卡片。
2. 根据 Job Case 当前状态生成一个推荐动作。
3. 显示推荐理由。
4. 用户点击后触发现有 workflow。
5. 用户可以忽略建议。

不需要一开始就做：

- 完整多 Agent 系统
- 自动执行所有任务
- 复杂评测平台
- 大规模个性化推荐

## 16. 面试叙事

可以这样讲：

> 我发现当前产品虽然已经有完整 workflow，但用户仍然需要自己判断下一步该做什么。因此我设计了 Case Manager Agent。它不是直接替用户做决定，而是观察当前 Job Case 状态，判断缺失环节，推荐下一步动作，并解释原因。用户确认后，它再调用现有 workflow 执行。
>
> 这样做的好处是，一方面保留了 workflow 的稳定性，另一方面让 AI 具备了 Agent 的关键能力：观察状态、判断下一步、解释决策、推进任务。

短版本：

> Case Manager Agent 是 OfferFlow 从工作流工具走向 Agentic Workspace 的第一步。
